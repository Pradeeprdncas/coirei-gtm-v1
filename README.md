# Coirei Onboarding MVP — numeric IDs + PostgreSQL/pgvector

A small **from-scratch starter implementation** of the onboarding flow. It is **not** a drop-in replacement for your existing Coirei backend, and its endpoints intentionally use simpler paths. It supports signup/login, one company as the workspace, an auto-created onboarding conversation, context upload, website text extraction, status, hybrid RAG, gap Q&A, product editing, per-product human verification, and onboarding completion. Campaign tables are **Phase-2 stubs** only.

## Practical scope

- Runs on Python **3.11/3.12** (recommended for a 2017 Intel Mac) and a remote PostgreSQL server with `pgvector` enabled, so you don't need Docker Desktop on your Mac.
- **No Redis**, browser rendering, OCR or hosted web-search dependency. `BackgroundTasks` is an **in-process MVP job runner**: restarting Uvicorn during a crawl can interrupt it. In production, move this to a durable task queue and add cancellation/retry/recovery.
- Scrapes **up to 12 same-site public pages**, with robots.txt and crawl-delay enforced. **Does not bypass robots, login pages, or CAPTCHAs**. Records `robots_blocked` or `needs_render` for the frontend. Some JS-heavy websites will require pasted text or document uploads.
- Saves extracted `.txt` under `data/sources/<company_id>/`. Stores source/version, cleaned text, quote provenance and structured JSON in PostgreSQL.
- FastEmbed `BAAI/bge-small-en-v1.5`: **384-dimensional**, small ONNX encoder (requires a one-time model download and some disk space). Hybrid retrieval merges Postgres full-text and pgvector cosine ranks with reciprocal rank fusion. If model installation/download fails, retrieval continues in `fts_only` mode. No fake embeddings.
- Supports **Ollama locally** (`http://localhost:11434/api`) and **Ollama cloud** (`https://ollama.com/api` with `OLLAMA_API_KEY`). Cloud may not support Ollama structured-output `format`, so this implementation uses JSON instructions + parsing; invalid output becomes `LLM_OPTIONAL` fallback, **not fabricated facts**. Ollama model names depend on what you have installed or selected.
- AI-generated market/ICP/value propositions are marked `ai_suggested`, confidence 65, pending review. Product facts need matching first-party quotes. Numeric pricing is only parsed from source text, and ambiguous cross-product pricing is left unassigned.
- Numeric IDs are auto-generated by the database. **Do not assume an ID value in frontend logic; use the returned integer.** IDs are always authorization-scoped to their owner.

## Start (recommended on your Mac)

```bash
cd coirei-onboarding-mvp
python3.11 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
# Fill DATABASE_URL and replace JWT_SECRET with `openssl rand -hex 32`.
# Make sure the database permits CREATE EXTENSION vector (Neon/Supabase support pgvector).
alembic upgrade head
# optional: ollama pull qwen2.5:3b-instruct
uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload
```

Docs and routes: `http://127.0.0.1:8000/docs`, `GET /health`.

**Use a disposable development database** while testing. No live DB, Ollama model, website crawl or full endpoint integration was executed inside this file-authoring environment. The code passes Python syntax compilation, but end-to-end operation depends on installing the requirements, configuring PostgreSQL, and running the integration checks below. This is a starter, not a production security or reliability certification.

## Small API contract

All protected endpoints require `Authorization: Bearer <access_token>`. Responses are generally `{"success":true,"status":"success","data":{...}}`. Errors use `{"success":false,"error":{"code":"...","message":"...","details":{...}}}`.

| Action | Method and path |
|---|---|
| Create account (optionally company) | `POST /auth/signup` |
| Login | `POST /auth/login` |
| Current user | `GET /auth/me` |
| Find/create company + onboarding conversation | `POST /companies` |
| List owned companies | `GET /companies` |
| Add website, prompt and/or files | `POST /companies/{id}/context` (multipart) |
| Live crawl progress and next action | `GET /companies/{id}/status` |
| Persisted onboarding chat/cards | `GET /companies/{id}/conversation` |
| Send company RAG chat message | `POST /companies/{id}/messages` |
| Ask missing-field questions (idempotent until answered) | `POST /companies/{id}/gap-questions` |
| Submit user gap answers | `POST /companies/{id}/gap-answers` |
| Continue with known data | `POST /companies/{id}/continue` |
| Company profile/edits | `GET/PATCH /companies/{id}/profile` |
| Source URLs and previews | `GET /companies/{id}/sources` |
| Product cards | `GET /companies/{id}/products` |
| Product detail, evidence, pricing | `GET /products/{product_id}` |
| Review/edit/accept product fields | `PATCH /products/{product_id}` |
| Verify one product | `POST /products/{product_id}/verify` |
| Complete onboarding | `POST /companies/{id}/complete` |

### Example request sequence

**1. Signup / create company**

```http
POST /auth/signup
Content-Type: application/json

{"email":"qa@example.com","name":"QA","password":"use-your-own-long-password","company_name":"Acme"}
```

Returns a bearer token and `company_id` if `company_name` was given. Otherwise call `POST /companies` with `{"name":"Acme","website_url":"https://example.com"}`. Existing owned domain/name is reused rather than duplicated.

**2. Add context, exactly like the onboarding input**

```bash
curl -X POST "http://127.0.0.1:8000/companies/1/context" \
  -H "Authorization: Bearer $TOKEN" \
  -F 'website_url=https://example.com' \
  -F 'prompt=Focus on pricing, ICP and features.' \
  -F 'files=@./sales-deck.pdf;type=application/pdf'
```

All three inputs are optional individually, but at least one must be provided. File cap: 5 MB per file, max 5; `.pdf`, `.docx`, `.txt`, `.md`. Scanned PDFs without embedded text are explicitly rejected (no OCR in MVP). Return includes numeric `job_id`, `status_url`, `conversation_url` and queued status.

**3. Poll status and render chat card**

```http
GET /companies/1/status
GET /companies/1/conversation
```

`/status` exposes `current_url`, `pages_done`, `pages_total`, `warnings`, `stage`, `next_action`. When finished, `/conversation` holds either the “needs a little more context” card or the verification-ready card as actual PostgreSQL messages (not UI-only state).

**4. If information is incomplete**

```http
POST /companies/1/gap-questions
POST /companies/1/gap-answers
Content-Type: application/json

{"answers":[{"question_id":12,"answer":"We charge subscriptions and usage credits."}]}
```

Up to four relevant questions; up to three **verified evidence-grounded** answer suggestions per question. It will return fewer or zero if the site does not support three; it never fabricates three choices just to fill slots. Free text is always supported. To bypass gaps: `POST /companies/1/continue`. To enrich again: call the same `/context` endpoint with more files, prompt, or site URL.

**5. Product fields and approval**

```http
GET /companies/1/products
GET /products/7
PATCH /products/7
Content-Type: application/json

{"revision":1,"fields":{"description":"An AI platform for...", "candidate_kind":"standalone_product"},"accept_fields":["key_features","main_use_case"]}
```

Only editable fields can change. The response has the new **product revision** and verification blockers. Editing changes mark those fields as explicitly user-provided; accepting an unchanged field marks it reviewed. Unreviewed required fields cannot be verified. If a product was auto-classified as a suite, explicitly reclassify it when appropriate—it is not silently promoted.

```http
POST /products/7/verify
Content-Type: application/json

{"revision":2,"status":"verified"}
```

Result `200` only after required product fields (`description`, `key_features`, `main_use_case`) are populated and accepted and the product is standalone; otherwise `409` gives blockers. Repeating with the **latest** revision returns `changed:false`. IDs are integer, and this is intentionally a **new URL** (the old v2 workspace verify route is not part of this MVP). **Do not point the existing frontend at the old URL and expect it to work without an API client change.**

**6. Finish**

```http
POST /companies/1/complete
```

Requires at least one verified standalone product and no unverified standalone products. Companies, products, source facts, chat cards, prices and evidence remain available through GET endpoints after completion.

### Suggested frontend adaptation

- Signup => POST `/auth/signup`; store Bearer token; use returned `company_id` or POST `/companies`.
- Connect website/files/prompt => POST `/companies/{id}/context`; navigate to conversation using the returned company ID.
- Conversation screen polls `/status` and `/conversation` until `next_action` is `verify_products` or `add_business_context`.
- Add Business Context => same `/context`; Answer Questions => `/gap-questions` and `/gap-answers`; Continue with Website Data => `/continue`.
- Overview tab => `/companies/{id}/profile`; Products tab => `/companies/{id}/products`; Product Detail => `/products/{id}`; Edit => `PATCH /products/{id}`; Verify => `POST /products/{id}/verify`.
- UI must hold the **product** revision separately from company revision, disable double-clicks, refetch on 409 and display blockers.

## Data model

The initial migration creates `users`, `companies`, `products`, `pricing_items`, `sources`, `chunks`, `field_claims`, `field_audits`, `conversations`, `messages`, `gap_questions`, `gap_answers`, `extraction_jobs`, and phase-2 tables `projects`, `campaigns`, `campaign_budgets`, and `campaign_results`. All PKs are numeric Postgres identity values. Sources retain structured JSON, text and content hash; claims preserve competing sources; reviewed user edits are audited and are not silently overwritten by extraction.

## Deliberate shortcuts and limits

- **Robots policy is always respected.** Never try to bypass robots.txt or CAPTCHAs. A disallowed route remains blocked; use user-provided files or explicit licensed APIs.
- `public_url()` does a DNS public-IP check, but DNS rebinding and changing DNS are still risks; production scrapers should use an egress proxy/firewall that blocks private networks at the network layer.
- One-process `BackgroundTasks` can lose jobs on restart. No durable retry or in-flight job heartbeat.
- No OCR, JS rendering, file malware scanning, refresh tokens, password reset, email verification, API rate limiting, audit-retention policy, or periodic worker.
- The first-party company structured-data extraction is intentionally conservative. Conflicting claims are stored instead of automatically resolved. AI-suggested fields are not equivalent to human-verified facts.
- Pricing parsing is intentionally narrow and might leave many prices `not_found` rather than misattribute a rival/child offer. Review all parsed prices before using them for budget calculations.
- "2–3 hours" is a reasonable target for installing and connecting a **thin prototype with AI help**; production-grade accuracy, security, and end-to-end acceptance will take longer.

```bash

# A named AI product on an isolated site (test account ONLY):
TEST_WEBSITE=https://your-test-site.example TEST_APPROVE=1 python scripts/e2e_smoke.py
```

Creates a unique disposable test user and writes **sanitized status/API evidence** to `reports/mvp-e2e-smoke.json`. By default it **does not** accept fields or verify products.
